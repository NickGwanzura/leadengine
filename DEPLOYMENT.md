# Dokploy deployment

Use a Dokploy **Docker Compose** application pointed at `compose.neon.yaml` (Neon) or `compose.yaml` (self-hosted PostgreSQL) in the repository root. Docker Stack mode does not support Compose `build` directives. Configure `app` as the domain target at container port 3000, enable HTTPS, redeploy after adding or changing the Compose domain, and set `AUTH_URL` to that exact HTTPS origin. Never expose the internal worker API through an alternate route. The app service's health check requires both PostgreSQL and Redis.

Set all variables in `.env.example`. Dokploy's environment editor writes a Compose `.env`; this file references the required values explicitly rather than assuming they are injected into each container. Generate each secret independently. In the local PostgreSQL stack, `DATABASE_URL` and `REDIS_URL` are constructed inside Compose from the service credentials. The Neon stack uses `NEON_DATABASE_URL` as `DATABASE_URL`; use an unpooled Neon URL so Prisma migrations run reliably. `ADMIN_EMAIL` and `ADMIN_PASSWORD` are only used by the one-off `seed` profile and should be removed after provisioning if possible.

Optional AI drafting uses the server-only `AI_PROVIDER`, `AI_API_KEY`, `AI_BASE_URL`, and `AI_MODEL` settings. Public-web Lead Discovery uses the official OpenAI Responses API with web search; `AI_DISCOVERY_MODEL` can override `AI_MODEL` when the configured model does not support web search. The app container receives these values; they are never returned by the status endpoint or sent to the browser. `AI_API_KEY` may be left blank to keep deterministic LeadOS features available without AI. The default provider is OpenAI-compatible; use an HTTPS base URL and a model supported by that provider. Add the API key in Dokploy's environment editor, never in chat, source control, or `NEXT_PUBLIC_*` variables. Outreach generation only runs after a workspace member confirms that the selected company's CRM/audit facts may be sent to the configured provider; drafts are saved for review and are never sent automatically.

Outbound email requires `RESEND_API_KEY`, a verified `RESEND_FROM` sender, `EMAIL_POSTAL_ADDRESS`, and `RESEND_WEBHOOK_SECRET`. Register `https://<your-domain>/api/webhooks/resend` in Resend and subscribe to email sent, delivered, delayed, bounced, complained, failed and suppressed events. Copy the endpoint signing secret into `RESEND_WEBHOOK_SECRET`. Sending stays disabled until those values are present. The Outreach Studio can send one reviewed cold/follow-up email at a time; it attaches the configured business postal address and an unsubscribe link, records provider status, and blocks addresses that opt out, bounce, complain or are suppressed by Resend. Do not use this first-stage sender for bulk campaigns. Verify SPF/DKIM/DMARC and a real reply-capable mailbox for the sending domain before sending live mail.

The app container starts its discovery worker alongside the web server. It waits for the app health endpoint, then every `DISCOVERY_INTERVAL_MINUTES` (default 10) asks the internal API to run the single most overdue search target, using the server-side OpenAI key. Targets are the segments from the lead engine profile (Lead Discovery → Analyse my business), or the six default Zimbabwean sectors until a profile exists. A completed target is searched again after `DISCOVERY_REFRESH_HOURS` (default 6), so eight segments make about 32 billable web searches a day; raise the value to reduce cost. Failed targets retry after 15 minutes. Each search saves at most five review candidates and excludes known CRM and previously sourced domains. The manual "Search all targets now" action starts fresh billable searches. Website analysis makes one AI request with up to 90 seconds allowed. The app supervisor restarts the discovery worker if it exits. Check the **app container logs** for `discovery-scheduler` messages and the Lead Discovery screen for latest run time, counts and failures. Set `AI_API_KEY` and use the official OpenAI endpoint in the app container. Discovery never imports candidates into the CRM or triggers crawls. When upgrading from the separate scheduler service, remove its orphaned container if Dokploy leaves it running.

On each deployment, the one-shot `migrate` container runs `prisma migrate deploy`. The application depends on a successful migration; the worker depends on a healthy application. Named volumes persist local PostgreSQL and Redis. For the local PostgreSQL stack, configure scheduled backups in Dokploy; for Neon, configure Neon backups and restore points. Test restore and monitor storage use. Redis persistence aids recovery but PostgreSQL remains the durable job store.

For crawler security, keep the worker on an isolated Docker network where practical and apply outbound firewall policy on the host or deployment platform that allows DNS and public HTTP(S) only. The built-in proxy denies private, reserved, nonstandard-port and mixed-answer DNS targets, then pins the connection to a validated IP. The worker does not intentionally execute JavaScript, follow redirects, submit forms or bypass access controls. Only approved domains are accepted by the result API. Review target terms before approving crawls.

The Python worker image installs Chromium and is larger than the web image. Allocate at least 2 GB RAM for it. Increase resources only after observed need. The Docker Compose service has a 2 GB memory limit. Monitor `CRAWL4AI_EXTRACTION_FAILED`, lease-expired and robots-denied error classes. Never log secrets or raw scraped HTML.

The Dokploy worker has been smoke-tested against a public test site using its deployed egress proxy and Crawl4AI. A site resolving to the same public IP as the Dokploy host may time out from inside the worker when the host network does not support hairpin routing; resolve that at the network or target-host layer, without bypassing the public-address safety checks.

The npm production audit currently reports zero advisories. The full audit still reports development-tool advisories in ESLint/Prisma tooling dependencies; these are not included in the application runner image. Keep the build environment patched and review updates before changing major Prisma versions.
